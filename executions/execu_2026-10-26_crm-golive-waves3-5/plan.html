TAVI CRM go-live retest · Gate 1 · Waves 3, 4 and 5 in parallel

Parallel run plan

Draft for review · 26 Oct 2026 · staging-crm.taviportal.com (NDC-Staging) · reference Zoho CRM org943261092 (read-only)

Each wave is a full feature retest, as agreed: every function of every feature in the wave, with old tickets rechecked inside it. The three waves run at the same time in three separate lanes. Anything that changes a setting for the whole tenant waits for one short serial window at the end, so the lanes can't break each other's results.

Nothing runs until you approve this plan. Answer the Gate 1 questions at the bottom; I then take the snapshot and start the three lanes.

Why not just run everything at once

RiskWhat would go wrongHow the plan avoids it
Wave 3 rules act on other lanes' recordsWorkflow, assignment, review and approval rules fire on any new lead or deal, including Wave 4's web-form leads and Wave 5's test records. Results get mixed up.Every Wave 3 rule has a criteria on its own name prefix ("QA AEO") and runs on its own restricted copy of the layout, as the suite already does. Waves 4 and 5 use their own prefixes.
Wave 5 changes fields and layouts that Wave 3 usesAdding a field, a validation rule or a layout rule on Leads or Transactions can make Wave 3's record saves fail.Wave 5 builds its fields, layouts, validation rules, layout rules and dependencies on a new module "QA W5 Module", never on Leads or Transactions during the parallel phase.
Tenant-wide settingsCRM ⇄ Desk integration on/off, business hours, fiscal year, company details and pipelines change behaviour for everyone.Read-only checks during the parallel phase; edits only in the serial window after Wave 3, each set back at once.
Sign-in rate limit (429)The owner account was rate-limited once on 25 Oct.Each lane signs in once per account and reuses it; the lanes use different accounts (table below). On any 429 that lane stops; no retries.
Known blockers from Wave 2Deals can't change pipeline (W2-B4) and Settings › Pipelines doesn't load (NDC-2386).Deal-stage and blueprint cases use the "Standard (Standard)" pipeline, as the suite already does; pipeline settings cases are marked blocked.

Steps for each lane

  1. Prepare: a snapshot of everything the wave can touch (rules, processes, forms, templates, modules, layouts, settings, users' profiles), plus the Plane state of each ticket.
  2. Run: API and screen together for every case; automation written as it goes and rerun once to prove it.
  3. Check against Zoho: the same function opened in Zoho, read-only, for every retested ticket and every candidate bug.
  4. Verify: every candidate bug re-run once from scratch before it is reported; test mistakes are fixed, not reported.
  5. Evidence: one annotated image per retested ticket and per candidate bug, pass or fail, in the approved layout (TAVI left, Zoho right, text under each, the same box numbers on both sides).
  6. Clean up: delete everything with the lane's prefix, purge it from the recycle bin, restore every changed setting, then a diff against the snapshot.
  7. Report and Gate 2: one report per wave. Nothing goes to Plane until you approve it.

What I will not do

  • Save anything in Zoho.
  • Change or remove existing email connections, web forms, rules, processes, blueprints or integrations that are not ours.
  • Send SMS or WhatsApp, buy credits, or invite real portal users.
  • Retest or move the 11 Wave 1 tickets that are In Progress.
  • Retry after an HTTP 429.
