The Standard ticket layout cannot be saved

Jam 66d8afd1 · 8 Nov 2026, 08:50 UTC Environment staging-desk.taviportal.com (NDC-Staging) Recorded on Edge 156, Windows 10, as ndc-staging-owner Investigated 8 Nov 2026
Root cause · confirmed

When you click Save, the layout editor sends a copy of the Create view as the Detail view. On the Standard layout, the Detail view holds fields that are not on Create, including the required resolution field, so they are left out of the request and the server rejects it with a 422.

The stored layout is correct, so this is not a data problem. I captured the full save request in a live repeat of the steps, with every write to the server blocked so nothing was changed.

Findings

F1 Saving the layout overwrites the Detail view with the Create view High · confirmed

Whatever is changed, the editor builds views.DETAIL from the Create view's sections. Any field or section that exists only on Detail is dropped from the request. On Standard this always includes resolution, so the server blocks every save of the default ticket layout.

Impact Admins cannot save any change to the Standard layout, including label edits, field moves and new fields.

F2 Data loss on any layout with its own Detail view High · risk

The 422 only happens because resolution is protected. Fields that are not protected are dropped from Detail without any warning. On Standard, the whole Integration section (crm_deal_id, contract_id) would disappear from the ticket detail page as soon as the save goes through.

Supporting observation All 10 other ticket layouts (QA NDC …) have a Detail view identical to Create, and none has the Integration fields. That matches F1 having already flattened them on earlier saves. This is an inference; I did not see those saves.

F3 The rename is half-saved, and the message says nothing was saved Medium · confirmed

The label PATCH runs first and succeeds (the field's label became “Email”), then the layout PUT fails and the toast says “Layout not saved”. The layout keeps its own copy of the label, so at 09:37 UTC, 47 minutes after the Jam, the Create canvas still showed “test”. The copy changed to “Email” at 09:47:42 UTC, written by the system user a7a7a7a7-…-0004. I did not trigger that change; my test edits were on Phone and never reached the server.

Impact The user is told the change failed while part of it was saved, and the canvas can show a stale label afterwards.

F4 The error message asks for an action the user cannot take Low · confirmed

The toast says “Move them instead”. The user is on the Create tab, where Resolution does not exist, and did not remove it. The message is accurate for the request but not for anything the user did. Once F1 is fixed it should not appear, but it should name the view (Detail) when it does.

Where the fix belongs

  • Layout editor (frontend). Keep each view (Create, Quick Create, Detail) as its own state and send each one from its own state on Save. If the editor is meant to keep Detail in step with Create, it must merge (keep the fields and sections that exist only on Detail) rather than replace.
  • Save order. Send the label PATCH and the layout PUT as one action: run the PUT first, or roll the label back when the PUT fails, and make the message say exactly what was saved.
  • Backend check. The 422 rule is correct and prevented data loss here. Keep it.

The TAVI Desk source code is not in this QA repo, so I couldn't point to a file or line. The behaviour above is from the live staging build on 8 Nov 2026.

How to reproduce

  1. Sign in to staging-desk as an admin and open Setup › Modules & Fields › Tickets › Layouts › Standard.
  2. On the Create tab, click any field label (for example Phone), change the text and press Enter.
  3. Click Save.
  4. Expected: the layout saves and the Detail view keeps Resolution and the Integration section.
    Actual: “Layout not saved: "resolution" cannot be removed from the layout…”, and the label rename is saved anyway.

How this was checked

  • Jam timeline, network bodies (the recorded PUT body was cut at 4 KB of 16 KB, so it could not settle the cause), and video frames.
  • Read-only API calls as an admin other than the reporter: the Standard layout, every ticket layout, and the ticket fields.
  • A repeat of the steps in a headless Edge browser with all writes intercepted. The label PATCH got a fake 200 so the editor would go on to send the PUT. The PUT was captured and never sent. I ran it twice: editing straight away, and opening the Detail View tab first.
  • A before/after read of the Standard layout to confirm nothing changed apart from the system label sync in F3.
