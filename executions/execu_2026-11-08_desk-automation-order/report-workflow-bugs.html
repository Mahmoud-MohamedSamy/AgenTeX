WF-01 High Security case O4

Webhook header value with a line break adds an extra header to the outgoing request

vs Zoho: BUG Zoho workflow rules have no Webhook action and Zoho webhooks have no custom headers (live: action menu has no Webhook; help "Setting up webhooks"). Not a parity bug — a security defect in a TAVI-only feature.
Zoho screenshot

Steps

  1. Make a rule with a Webhook action to a request catcher (webhook.site).
  2. Add a header X-QA whose value is a + line break + Injected: 1 (saved through the API).
  3. Create a ticket that fires the rule.

Expected

Header names and values containing a line break are refused at save ("Header values can't contain line breaks"), and reserved headers such as Host are refused; only the configured headers are sent.

Actual (TAVI)

The receiver got two headers: x-qa: a AND injected: 1. A Host header override is also accepted (the dispatch then stays Pending with "The SSL connection could not be established").

Proved on webhook.site 12 Nov 10:03 UTC. Screen input not tried (the header box may block line breaks); the API accepts it.

WF-02 High Security case O1

Script saved in an Add Comment action body runs when an admin opens the rule

vs Zoho: BUG Not documented in Zoho; no Zoho behaviour to copy. Security defect regardless.

Steps

  1. Save a rule (through the API) whose Add Comment body contains <img src=x onerror="window.__xss=1">.
  2. As an admin, open the rule in the editor.

Expected

Text entered in any action field is always shown as plain text in the rule editor; no script runs.

Actual (TAVI)

The script runs in the editor (window.__xss is set). Name, description, list, Execution History and the ticket comment are all safe.

API-only input, but the editor is the one rendering it unsafely.

WF-03 High Bug case G4

Double-clicking Save & Activate creates two identical rules

vs Zoho: BUG Zoho help is silent; not tried live (it would create Zoho rules). Standard behaviour, kept as a bug.

Steps

  1. Settings › Workflow Rules › New Rule; fill a valid rule.
  2. Double-click Save & Activate.

Expected

One rule is created; Save is disabled while the first save is in progress.

Actual (TAVI)

Two identical active rules were created. Seen twice on 12 Nov ("QA AO WF C5 …" ×2 and "QA AO WF G4 dbl" ×2, confirmed by the API list).

Both pairs were deleted after the test.

WF-04 Medium Bug case G5

Saving a rule silently overwrites a change made meanwhile by someone else

vs Zoho: BUG Zoho help is silent on concurrent edits. Kept as a data-loss bug, not a parity one.

Steps

  1. Admin A opens a rule in the editor.
  2. Meanwhile the rule is renamed by someone else (second tab / API PATCH, 200).
  3. Admin A changes the description and clicks Save.

Expected

The second save is refused with a "rule was changed, reload" message; no change is lost.

Actual (TAVI)

The save succeeds with no warning; the other person's rename is lost (name back to the old one).

The save body carries no version, so the server cannot detect the conflict.

WF-05 Medium Bug case M6

Execution History shows rule and record as raw ids, and the record is not a link

vs Zoho: NO ZOHO Zoho Desk has no execution-history page (help: runs show only in the ticket History with the rule name, actor "Workflow"). TAVI's page is an extra.

Steps

  1. Open Setup › Execution History (/settings/workflow-executions).

Expected (no Zoho equivalent)

If kept: rule and record shown by name, record opens the ticket (as TAVI's ticket History already does).

Actual (TAVI)

Both columns show UUIDs (e.g. 53c7ed55-…, which is the existing rule "QA AO WF P12od"); the record is plain text, not a link. The API also returns originName: null on all 200 latest rows.

Together with B-6 (no menu link) this page is hard to use.

WF-06 Medium Bug case F18

${recordId} and ${moduleId} render empty in a Field Update

vs Zoho: DIFFERS Zoho placeholders render the ticket's values, incl. ${Cases.Request Id} = the ticket ID/number (help "Creating and managing email templates"). TAVI's ${recordId}/${moduleId} render empty although its help lists them.

Steps

  1. Rule On Create, Field Update Description = R[${recordId}].
  2. Create a ticket.

Expected (Zoho Desk)

A placeholder for the ticket's ID renders the ID (Zoho: ${Cases.Request Id} → the ticket number); no listed placeholder renders empty.

Actual (TAVI)

Description = R[]; same for ${moduleId}. ${subject} works, $${x} gives ${x}, an unclosed ${subject stays literal (all correct).

WF-07 Low Finding case I30

"Send happiness email" says Succeeded while ratings are switched off

vs Zoho: BUG Zoho: what happens while ratings are off is not documented (rating email sent by an Alert with ${Cases.Customer Happiness Rating}). Checked against TAVI's own help text.

Steps

  1. Customer Happiness off (original tenant setting).
  2. Rule with action Send happiness email; create a ticket.

Expected

Nothing is sent and the execution says it was skipped because ratings are off (not "Succeeded").

Actual (TAVI)

Dispatch SendHappinessEmail Succeeded, no reason, nothing in the ticket history.

Same blind spot as P18 (skipped agents shown as Succeeded).

WF-08 Medium Finding case E9

A criteria pattern that leaves a condition out is accepted; the condition is silently ignored

vs Zoho: DIFFERS Live Zoho: pattern "1" with 2 conditions → red "Numbers in this pattern do not match with the numbers used in the Criteria Editor"; OK does not apply it.
Zoho screenshot

Steps

  1. Rule with 3 conditions.
  2. Edit Pattern → 1 and 2 → Apply → Save.

Expected (Zoho Desk)

A pattern that does not use every condition number (or uses one that doesn't exist) is refused with "Numbers in this pattern do not match with the numbers used in the Criteria Editor", and the rule can't be saved with it.

Actual (TAVI)

Accepted: condition 3 stays on screen but is not part of the criteria. Other pattern errors are good ("Pattern ends unexpectedly.", "Missing closing parenthesis.", "Pattern refers to condition 4, which doesn't exist."). 1 and 2 or 3 is read as ((1 and 2) or 3) without asking.

WF-09 Medium Finding case L1

Test rule ignores the sample record id

vs Zoho: NO ZOHO Zoho has no test/dry-run for workflow rules (help FAQ: test by creating a real ticket). TAVI extra.

Steps

  1. Open a saved rule › Test rule.
  2. Enter the id of a ticket that matches, leave the field values JSON empty, run.

Expected (no Zoho equivalent)

If kept: the sample record's values are used when no values are typed.

Actual (TAVI)

"Not matched" unless the values are typed in as JSON. The panel's example JSON is CRM-style (revenue, intValue). Nothing is saved (correct).

Seen through the same API the panel calls: POST /workflow/rules/{id}/execute {recordId, triggerKind, fields}.

WF-11 Low Finding case C4 / C7

Name and description limits are only enforced at save

vs Zoho: DIFFERS Live Zoho: the Rule Name box has maxlength 50 and stops typing at 50 characters; the Description box has no limit.

Steps

  1. Type a 1000-character rule name (or a 5000-character description).
  2. Save.

Expected (Zoho Desk)

The rule-name box stops at the limit while typing (Zoho: 50); no surprise error at save. Description: no limit is needed (Zoho has none), so the 2000 server limit should be shown on the box if kept.

Actual (TAVI)

No limit in the box; the server refuses at save: name 200 ("must be 200 characters or fewer"), description 2000.
