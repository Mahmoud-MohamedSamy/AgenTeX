
===== NDC-2863 Data Backup: a backup made today cannot be restored ("made before restore was available")
Summary
A custom backup created today finishes normally but is marked as not restorable, and restoring it into a sandbox is refused with a reason that cannot be true for a backup made minutes earlier.
Steps to reproduce
- Sign in to Desk as the account owner.
- Go to Setup, Data Administration, Data Backup, and create a custom backup for yesterday to tomorrow, without attachments.
- Wait until the backup shows as completed.
- Choose Restore into a sandbox for that backup.
Expected result
The backup can be restored into a new sandbox.
Actual result
The backup completes but has restorable = false. Restore is refused (422, BACKUP_NOT_RESTORABLE) with "This backup cannot be restored: it was made before restore was available, or it has expired." The backup was made the same day and expires on 18 November.
Additional notes
Reproduced twice on 11 November 2026. A full backup, which might be restorable, is blocked until 23 November by the one-per-30-days rule, so no backup on this company can be restored at the moment. This blocks the backup-restore part of NDC-2012. The test backup was deleted afterwards.
Environment
staging-desk.taviportal.com, API, 11 November 2026, owner account.

===== NDC-3230 Workflow Rules | A rule update that leaves out the conditions clears them, so the rule runs on every ticket (Zoho keeps them)
Summary
When a workflow rule is updated and the request does not include the rule's conditions, TAVI clears them. The rule then runs on every ticket of its trigger in its departments, with no warning. Zoho Desk keeps the conditions in that case and clears them only when they are sent explicitly as empty. The TAVI editor relies on the current behaviour, so the fix needs a matching editor change.
Steps to Reproduce
- Create an active On Create rule on Tickets with the condition Subject starts with "QA" and any action (e.g. Add Tags).
- Update the rule through the API with only its actions: PATCH /api/v1/workflow/rules/{id} with body { "actions": [ … ] }.
- Open the rule in the editor (or read it with GET /api/v1/workflow/rules).
- Create a ticket whose subject does not start with "QA".
Expected Result
- The conditions are kept (Subject starts with "QA"); only the actions change.
- Conditions are cleared only when the request says so explicitly ("criteria": null).
Actual Result
- The update is accepted (200) and the conditions are gone (criteria: null). The editor shows "No conditions — actions run on every event of this trigger".
- The rule runs on every new ticket — in the test it fired on 6 unrelated tickets at once.
Impact
- Who can trigger it: any caller of the workflow API that sends a partial update — an integration, a script, an admin tool, or a future TAVI feature that edits rules (bulk edit, import, copy). People using the TAVI editor are not affected today (see below).
- What happens: one call silently turns a rule into "every ticket". If the rule is active, all its actions run on every matching event across its departments: fields, owners or status changed on all tickets; emails sent to customers or agents; webhooks fired to outside systems; tags, tasks or comments added everywhere.
- Detection and recovery: no warning; the only signs are "No conditions" in the editor and a burst of runs in Execution History. Field changes and sent emails cannot be rolled back.
- Parity: an integration written against Zoho's behaviour (conditions kept on partial update) will hit this.
What the TAVI editor does today (captured 23 Nov)
- Change only an action and save → the editor sends the whole rule, conditions included. Conditions kept.
- Remove all conditions and save → the editor sends the rule with no conditions field at all; the API stores criteria: null. So the editor relies on "conditions left out = no conditions".
Zoho Desk (checked live 23 Nov)
Tested with Zoho assignment rules, which use the same conditions format (Zoho workflow rules cannot be created through its API):
- Rename only, no conditions in the request → conditions kept.
- Change the assigned agent only, no conditions in the request → conditions kept.
- criteria: null sent explicitly → conditions cleared.
Environment
- App: Anyware Desk (staging) — staging-desk.taviportal.com (NDC-Staging), owner account
- API + Microsoft Edge, Windows 10; Zoho Desk test portal for the comparison
- Dates: 22–23 Nov 2026

Checked on tavi through the API, 25 Nov: a probe rule with Subject starts with "QA" kept its condition after an update that sent only its actions, and after one that sent only its name. Sending "criteria": null still cleared it. The probe rule is deleted and purged.
Not checked live: removing the last condition in the editor and saving. Tests cover it.
  [2026-11-24T14:15] Reproduced on tavi (NDC Staging), 24 Nov: a probe rule with Subject starts with "QA" read back with no conditions (criteria: null) after an update that sent only its actions, and again after one that sent only its name.
