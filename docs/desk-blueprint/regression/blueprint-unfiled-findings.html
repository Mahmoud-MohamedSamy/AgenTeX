EN-13MediumFile (differs from Zoho)

Blueprint | A ticket created in a middle status enters at the start state and its status is reset to Open

Steps

  1. Blueprint with states Open → Escalated → Closed whose criteria match a new ticket (e.g. Subject contains "QA").
  2. Create a ticket with Status = Escalated (New Ticket screen or API).
  3. Open the ticket: Steps card, Status and History.

Expected

Like Zoho Desk (checked live 18 Nov 2026): the ticket enters the blueprint at Escalated and keeps Status = Escalated.

Actual

The ticket enters at Open and its Status is changed to Open, with no History line for that status change. An existing ticket edited to match while Escalated does enter at Escalated, so create and edit behave differently.

Labels: Blueprint. Zoho evidence: 18 Nov live check (ticket created in Escalated entered at Escalated). Case EN-13.

UX-01LowFile

Ticket | In Arabic the blueprint progress bar shows status names in English

Steps

  1. Switch Desk to Arabic.
  2. Open a ticket that is in a blueprint.
  3. Compare the progress bar under the subject with the status chip in the ticket list.

Expected

The progress bar shows the translated status names, the same as the ticket list ("مفتوحة" for Open, "مغلقة" for Closed).

Actual

The progress bar shows "Open" and "Closed" in English (and "Closed" next to the flag), while the ticket list beside it shows "مفتوحة". The rest of the page (Steps card, buttons, tabs, footer) is translated and right-to-left.

Labels: Blueprint, i18n. Evidence screenshot already taken: evidence/ui/P3-UX-ar-ticket.png. Side note: the left navigation item "Approvals" also stays English in Arabic (not blueprint-specific).

TF-09LowFile or document

Blueprint | A custom action in After-transition actions does not run in the order shown

Steps

  1. Transition with After actions in this order: Webhook 1 → Run Custom Action → Webhook 2 (all to a request receiver).
  2. Run the transition.
  3. Compare arrival times at the receiver.

Expected

Actions run in the order shown — the designer says "Run in this order once the ticket moves."

Actual

Webhook 1 and Webhook 2 arrive in the same second; the custom action placed between them arrives about 3 s after Webhook 2, because it is handed to Workflow and runs separately.

Labels: Blueprint. Either keep the order (wait for the custom action) or change the hint to say custom actions run after the others. Case TF-09.

ST-05 · ST-07LowDecide (API only)

Blueprint API | A state can be saved with a business-hours set or an escalation email template that does not exist

Steps

  1. POST /api/v1/modules/{tickets}/blueprints with a state whose "slaBusinessHoursId" is a random id.
  2. Save another blueprint whose state has an escalation level with "templateId" = a random id.
  3. Open both in the designer; let a ticket reach the escalation level.

Expected

Both saves are refused, as other unknown ids already are (owners, teams, custom actions, approver teams).

Actual

Both saved (201). The designer then shows "Deleted business hours (the default hours count)" / "This email template was deleted". At runtime the level with the unknown template still sent its in-app notifications (4 to the owner); the email part cannot be confirmed.

Labels: Blueprint, API & Platform. The designer cannot create this on its own; it only happens through the API or when a set / template is deleted later (then the designer's message is the right behaviour). Cases ST-05, ST-07.

CV-06 · API-01LowDecide (API only)

Blueprint API | A transition with no name and a 2,000-item checklist are saved

Steps

  1. POST /api/v1/modules/{tickets}/blueprints with a transition whose "name" is "".
  2. Save another with a transition checklist of 2,000 items.

Expected

Empty name refused (the designer shows "The transition from Open to Escalated needs a name"); a sensible checklist limit with a clear message.

Actual

Both saved (201). All other wrong shapes tested (strings for numbers, objects for arrays, unknown action kinds) are refused with 422, never 500.

Labels: Blueprint, API & Platform. The designer blocks the empty name, so this is API-only. Cases CV-06, API-01.

TF-X1LowDecide (API only)

Blueprint API | Create-task action with an unknown assignee mode is saved and assigns the ticket owner

Steps

  1. Save a transition whose After action is createTask with "assigneeMode": "specific" (valid values: owner, performer, user, team).
  2. Run the transition.
  3. Open the created task.

Expected

The save is refused: unknown assignee mode.

Actual

Saved (201); the task is created and assigned to the ticket owner. With mode "user" + an agent the task goes to that agent (correct).

Labels: Blueprint, API & Platform. Found while testing TF-04.

RS-01 noteLowCheck first

Ticket History | One owner change is shown as two lines ("Ticket Owner was updated" and "Ticket owner was changed")

Steps

  1. Assign a ticket in a blueprint to an agent.
  2. Open the ticket's History tab.

Expected

One line for the owner change.

Actual

Two lines with the same time and values: "Ticket Owner was updated — Old blank, New Customer Experience Specialists 1" and "Ticket owner was changed — Old blank, New Customer Experience Specialists 1".

Labels: Ticket History. Seen on ticket #7562 (P3-RS-history-esc.png). Not blueprint-specific — check whether it happens on a ticket outside any blueprint before filing; may be a duplicate of an existing History ticket.
