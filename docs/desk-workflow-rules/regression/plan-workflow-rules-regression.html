API-01 · FINDING · Medium · Ready to file — Desk Workflow Rules | A rule update that leaves out the conditions clears them, so the rule runs on every ticket (Zoho keeps them)

Steps

  1. Take a rule with conditions (e.g. Subject starts with "QA").
  2. Save a change that sends only the actions (API PATCH with only actions).
  3. Create any ticket.

Expected: The conditions are kept, or the save is refused.

Actual: The conditions are cleared, the rule becomes "All tickets" and runs on every new ticket (6 unrelated tickets in the test).

Before filing: What the TAVI editor does (captured 23 Nov): an action-only edit sends the whole rule with its conditions; removing all conditions sends the rule with NO criteria key, and the API stores criteria = null (editor then shows "No conditions — actions run on every event"). Zoho (live, assignment rules): leaving the conditions out of an update KEEPS them; only an explicit criteria: null clears them. To match Zoho: the API should keep conditions when the key is missing and clear them only on an explicit null — and the editor must then send criteria: null when the user removes all conditions, or clearing in the editor will stop working.

Environment: NDC-Staging, Desk → Tickets. FILED as NDC-3230 (23 Nov). Full ticket draft (not filed): api-01-ticket-draft.md. Run 1, 22 Nov.

Scope: every trigger and its sub-options, every condition operator for every data type, related Contact/Account fields and ticket facts, every action with all of its options, instant and scheduled, and the combinations between them. A full cross product (11 triggers × 26 actions × 93 operator cells × modes × scopes) is over 500,000 runs, so the plan covers combinations in three layers:

  1. Each part alone, fully — every trigger option (TR, TF, TD, TE), every operator (CO), every action option (AC, AT, AX). One simple partner for the other parts.
  2. Every pair that has a rule — trigger × action: all 286 cells checked at save time (MX), and each allowed action run for real under each trigger family (RC). Trigger × condition where the meaning changes, such as "changed" on create, Delete values, Date re-check, facts on ticket events (TC).
  3. Realistic stacks — several rules, order and chains (MR), other automation (IN), and 5 end-to-end journeys (E2E).

Up to 10 actions fit in one rule, so the runtime cells are packed: about 30 QA rules cover the 100+ runtime cells. Every QA rule has the guard condition Subject starts with "QA WF ", so teammates' tickets are never touched.

What the build offers today

Execute based on

  • A Record Action — Create · Edit · Create or Edit · Delete · Field Changed (watch 1+ fields, Any / All in the same save, "Also run when a record is created")
  • A Date-Time field — date field, N Minutes / Hours / Days before or after, Counting = Elapsed time or Business hours (minutes/hours only)
  • A Ticket Event — Customer Reply · Agent Response · Private Thread (incoming and outgoing / incoming / outgoing) · Comment (any / public / private) · Happiness Rating (all / Good / Okay / Bad), several at once
  • Rule Mode Recurring / One time · Layout scope · Department scope. Record Note and Score triggers are CRM-only and stay hidden in Desk.
