What it is, in one line

A validation rule checks one field's value when a record is saved. If the value is wrong, the record is not saved and the user sees the admin's message. In CRM the rule can also just warn and let the user save anyway.

Field to check: "Serial number"→Check: must match AA-12345678→Wrong? Show "Serial number must look like AB-12345678" and don't save

Why the business wants it

  • Clean data at the door. Bad values never get in: a discount over the limit, a phone without the country code, an end date before the start date, a code in the wrong format.
  • Company rules in the system, not in people's heads. "Retail deals can't have more than 15% discount" becomes a rule everyone meets, with the reason written in the message.
  • Hard stop or soft nudge (CRM). "Don't save" for rules that must never break. "Warn and allow saving" for things that are usually wrong but sometimes fine.
  • NDC uses it today. NDC's Zoho Desk has "Status = Reject needs a clear rejection reason". NDC's Zoho CRM has rules on Deals Stage and Calls status.
  • Customers too (Desk). With "Apply to Help Center", tickets customers submit are checked the same way.
  • Outside checks (CRM). A function rule can ask another system ("is this customer code real?") before the record is saved.

How it works technically

  • A rule belongs to one module and one layout (CRM can pick "All layouts"). Desk rules can be limited to departments.
  • It checks one field (the "field to check"). It has one or more conditions, checked in order. Each condition has an optional "Applies when" on other fields, a check on the field (is, contains, length, regex, greater than…), when to show the error (check matches / does not match) and a message in English and Arabic. The first condition whose "Applies when" fits decides.
  • The server enforces it. A save that breaks a rule gets 400 RECORD_VALIDATION_FAILED with the field, message and rule id. A warn rule gets RECORD_VALIDATION_WARNING; the screen asks the user and sends the save again with confirmed_warnings.
  • Field verification (CRM) checks the field while the user types (POST …/validation-rules/verify) and again on save.
  • Function rules (CRM) send the record to your HTTPS address (500–10000 ms timeout, optional signing secret) and use its answer: success, or an error message. If it can't be reached, the record is not saved.
  • Rules live at /modules/{id}/validation-rules: list, get, create, update (with a version number), delete, plus /verify and /{id}/test-function.
  • It is not the same as mandatory fields (only "not empty"), layout rules (show / hide / require fields while typing) or field permissions. Those are separate features, in Zoho too.

What is in TAVI today

  • A "Validation Rules" tab in module settings for every module, in CRM (15 modules) and Desk (10 modules), and a "Set Validation Rules" row menu.
  • List with search, filters (layout, status, mode, department), badges, Active switch, delete with confirm, and a "can't be applied" flag.
  • Editor: name, description, layout, field to check, departments and Help Center (Desk), rule type, behaviour, error placement, ordered conditions, regex gallery and tester, English and Arabic messages, function settings and a Test button.
  • Current data on NDC-Staging: CRM Leads has 1 rule ("QA LR1112 VR", left by the Layout Rules run). Desk Tickets has 1 rule ("QA NDC Reject needs a reason", 3 Nov), and the API flags it "A Desk validation rule applies to one layout; choose it." — checked in J7. The run leaves both as they are.
  • Older tickets: NDC-2646 (rules saved but never applied) and NDC-2536 (no rule on a pick list). The new build looks fixed for both; group R retests them first.
