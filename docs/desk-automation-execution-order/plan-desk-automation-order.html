What this means for testing

  • Skills first. Your quote leaves it out, but NDC-2275 (EO-1, decided 14 Oct) has Skills as step 1. I propose keeping it.
  • "Sequential > load balancing > skill based". Zoho doesn't explain this. NDC-2275 (EO-6) reads it as the three methods inside the round robin step: each target has one method and the first matching rule wins. It's not a priority between methods. I'd test first-match and check it live in Zoho.
  • Notifications last. Zoho never describes the case where two steps set the owner. NDC-2275 (EO-5) decided that only the final owner is told. Marked as our decision, not Zoho's documented behaviour.
  • Stale line. NDC-2275 EO-1 still says Blueprint is not built in TAVI. It is built now, so that step has never been tested as part of the order.

6. How I would run it

  • Tenant: NDC-Staging, tickets module 88e8ea44…. Never the Standard layout or shared rules.
  • Accounts: owner plus existing admin, supervisor and agent accounts. Each signs in once per run, because a second sign-in ends the first session. No credentials printed.
  • Evidence: screenshots for failed cases only, annotated side by side with Zoho. Anything only inferred about Zoho is marked "not checked".
  • If something blocks a case: I stop and tell you. No shared setting (business hours, master switches, Standard layout) changes without asking first.

Known blockers

  • Supervisor rules are not built, so those cases can only be gaps.
  • Customer-reply triggers need a real outside mailbox; earlier replies from anyware.software did not fire rules, Gmail did.
  • Suspending an agent was blocked by the permission check in October and may need you to run it or allow it.
  • Staging connection drops and idle agents going offline after 10 minutes can give false failures, so failures are re-run alone.
  • Other people work on staging at the same time and their rules may fire on my tickets. Rules are guarded by the prefix, and the baseline shows what else is active.

Automation and visual checks

  • Functional: Java suite in automation/, new feature deskautomationorder, reusing deskworkflowrules and deskblueprint. All classes run in one JVM with one sign-in per account, to avoid the sign-in rate limit and session revocation.
  • Automatic visual checks on every screen and state: clipped or overflowing text, overlapping elements, raw translation keys, broken images, console errors, and fields that don't match the saved value.
  • Screens captured: light and dark theme, English and Arabic (RTL), desktop and phone width, plus empty, error and long-text states.
  • Looked at by eye: I review the captured screens myself, and compare them with Zoho where a difference matters. A screen isn't called visually clean from the automatic checks alone.
  • Limit: a test that passes says nothing about how a screen looks, so the report gives functional and visual results separately, and says which screens were not reviewed.
