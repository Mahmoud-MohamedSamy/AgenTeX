TAVI Surveys test plan

This plan covers the TAVI Surveys module, which is modelled on Zoho Survey. It goes with the explainer page Zoho Survey, explained for the build team. It is written before the build starts, so each case states Zoho's behaviour as the expected result. When the PRD or the build differs, we update the case and do not raise a bug.

Reference: Zoho Survey (live trial + help centre)Target: NDC-Staging (CRM + Desk + Surveys)Plane: no ticket or PRD yet

1. Scope

In scope

  • Survey list and lifecycle: draft, published, closed, trash
  • Builder: pages, 28 question types, validation, logic, variables
  • Settings, themes, languages (Arabic RTL first)
  • Publishing: link, embed, pop-up, QR, email invites, unique links
  • Restrictions and quotas
  • Respondent pages on desktop and mobile
  • Responses, reports, NPS/CSAT maths, exports
  • CRM and Desk hooks, trigger email, webhook
  • Roles, sharing, audit log, encryption
  • Survey API (whatever TAVI exposes)

Out of scope for now

  • Buying panel responses (Zoho "Buy Responses")
  • Native offline/kiosk mobile apps, until the PRD includes them
  • Third-party apps outside TAVI (Mailchimp, Salesforce, Slack…)
  • Zoho plan gating. TAVI licensing gets its own cases once defined
  • AI survey creation, unless it is in the PRD

Questions for product

  • Standalone app, or a module inside CRM/Desk?
  • Which question types are in release 1?
  • Limits: questions per survey, answer length, file size, responses
  • Do respondents need a login for internal surveys?
  • Which languages ship first (Arabic, English)?

2. Approach

  • Follow the build phases. The catalogue below is tagged with the six phases from the explainer. Each phase is tested when the devs hand it over, and earlier phases get a regression run.
  • Zoho is the oracle. Where the PRD says nothing, we compare against Zoho Survey in the trial portal (read and write allowed there, with cleanup). A parity difference is filed only if the PRD asks for parity. TAVI extras are not bugs.
  • Two layers: builder and respondent. Each builder feature gets a builder case (can I set it up?) and a runtime case (does the respondent see the right thing?). Most survey bugs show up at runtime.
  • Data checks. Every runtime case confirms the stored response through the response view or the API: status, answers, metadata, variables.
  • Automation. P0 and P1 runtime and API cases go into the Selenium/TestNG framework as a new surveys feature (page objects for builder, respondent page and responses). The respondent page is public and needs no sign-in, so it is the cheapest place to automate first.
  • Priorities. P0 blocks release (core flow, data loss, security). P1 is main functionality. P2 covers edge cases, cosmetics and rare paths.

4. Environment and test data

Environments

  • NDC-Staging: CRM, Desk and the Surveys app
  • Zoho Survey trial (portal 948695391) for comparison. The trial ends early December 2026; ask for a new trial before Phase 3
  • A plain static test page for embed and pop-up tests
  • Test mailboxes for invites, reminders, resume links and trigger emails

Accounts

  • Owner/admin
  • Department admin, user, contractor, report viewer (or the TAVI equivalents)
  • A user with no Surveys access
  • Anonymous respondent (fresh browser profile)

Seed surveys

  • QA-ALL: one of every question type
  • QA-LOGIC: 6 pages with skip, display, answer display and disqualify rules
  • QA-NPS: NPS + Likert + star, for metric maths
  • QA-AR: Arabic default with an English translation
  • QA-BIG: 200 questions, plus a response generator for 10k rows

All test records are prefixed QA SV. A ledger is kept in the run folder, and everything is deleted (and purged from trash) after each run.

5. Entry and exit criteria

Entry (per phase)

  • PRD or ticket for the phase exists, or product confirms "match Zoho"
  • Build deployed on NDC-Staging with release notes
  • Devs' smoke check passed: create survey, add question, open link, submit
  • Test accounts and seed data ready

Exit (per phase)

  • 100% of P0 and 90%+ of P1 cases run
  • No open P0 bug; P1 bugs have an agreed fix date
  • Calculation cases match the hand-made spreadsheet exactly
  • Earlier phases' P0 regression passes
  • Results report published; test data cleaned (ledger at zero)

Suspension

  • Respondent page cannot submit
  • Responses are lost or attached to the wrong survey
  • Builder cannot save
  • Staging down for more than half a day

10. Deliverables and defects

  • Per phase: a test-run checklist page with status per case, a results report with evidence screenshots (failed cases shown next to Zoho), and a cleanup ledger.
  • Bug titles follow Surveys | Descriptive title. Bugs are drafted first and filed to Plane only after your go.
  • Automation: a surveys feature in the Selenium framework with a feature map, so retests reuse it.
  • A gap list against Zoho after Phase 1, filed as one "missing functions" item if you want it.
